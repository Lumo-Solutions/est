# Deployment deltas vs MASTER_SRS.MD §6

`deploy/docker-compose.yml` reproduces the SRS §6 template verbatim for
`postgres`, `redis`, `seaweedfs`, `vllm`, `backend`, `frontend` (same images,
env var names, volumes, ports). Everything below is an addition required to
satisfy SRS §5 (Keycloak, MFA, RLS, TLS, encryption) or to make the stack
actually runnable; each is marked inline in the compose file with a
`# --- addition ---` comment.

| Area | Delta | Reason |

Same internal/public split already used for `KEYCLOAK_BASE_URL`/`KEYCLOAK_PUBLIC_URL`. Found while building Phase 8b's PDF viewer; see `docs/module-frontend-phase8b-plan.md`. |

### Local development on Windows (Git Bash)

- **Run `make` targets from Git Bash, not PowerShell or cmd.exe.** The
  Makefile and every script under `deploy/` are POSIX shell (`set -a; . ...`,
  `bash foo.sh`); PowerShell doesn't have `.` source, `set -a`, or the same
  quoting rules and will fail or silently do the wrong thing.
- **Scripts that `docker exec`/`docker run` with an absolute container path**
  (`/opt/keycloak/bin/kcadm.sh`, `/var/run/docker.sock`, etc.) must set
  `export MSYS_NO_PATHCONV=1` first. Git Bash's MSYS layer rewrites
  leading-`/` arguments into Windows paths (e.g. `/opt/...` →
  `C:/Program Files/Git/opt/...`) before they ever reach `docker`, which
  breaks the call on the container side. `deploy/keycloak/bootstrap.sh` and
  `deploy/keycloak/dev-token.sh` already export it themselves; if you invoke
  `docker exec`/`docker run` with an absolute path directly at the Git Bash
  prompt (not through one of those scripts), export it in your shell first,
  e.g. `export MSYS_NO_PATHCONV=1 && docker exec ... /opt/keycloak/bin/kcadm.sh ...`.
- This is a Windows/Git Bash-only concern; it's a no-op on Linux/macOS.

### Getting a bearer token for local API testing (dev-token.sh)

**Dev only -- never run against a shared or production Keycloak.**
`deploy/keycloak/dev-token.sh` (via `make dev-token`) temporarily enables
the password grant on `installtec-backend`, clears a seeded demo user's
required actions (TOTP enrolment, temp password) and gives it a permanent
password, then requests and prints a real access token to `.dev-token`
(gitignored). This exists because the interactive Authorization Code login
form doesn't work over plain HTTP locally (see the "Cookie not found"
section of `docs/keycloak-setup.md`) -- it's the fastest way to get a valid
token to `curl` the API with:

```bash
make dev-token   # defaults to estimator1 / Estimator1Pass!
curl -s -H "Authorization: Bearer $(cat .dev-token)" http://localhost:8001/api/v1/auth/me
```

Pass a different seeded username/password directly (`bash
deploy/keycloak/dev-token.sh procurement_head1 ...`) to test other roles;
see `bootstrap.sh` for the full list of seeded demo users.

### Keycloak `sub`/`acr` claim bug (tokens rejected with no `sub`)

A realm import that defines its own `clientScopes` (ours does, via
`installtec-claims`) does **not** get Keycloak's built-in `basic`/`acr`
client scopes for free -- those are what normally emit the `sub` and `acr`
claims. Without them, every access token Keycloak issued was missing `sub`
entirely, and `TokenValidator.validate()` (`backend/app/security/jwt.py`,
`options={"require": [..., "sub"]}`) hard-rejected every single token. Fixed
two ways so both a fresh import and an existing realm pick it up:
`realm-installtec.json` now defines `sub`/`acr` protocol mappers directly on
`installtec-claims`, and `bootstrap.sh` idempotently adds them via `kcadm.sh`
if they're missing (covers a realm that was imported before this fix). See
`docs/keycloak-setup.md` for the token-validation side of this.

### Populating the ONNX embedding model volume

`OnnxEmbedder` (`backend/app/integrations/embeddings.py`) looks for the
model at `$ONNX_MODEL_DIR/<embedding_model with "/" replaced by "_">`, e.g.
`/models/BAAI_bge-small-en-v1.5` for the default `EMBEDDING_MODEL`. On a
machine with network access to both HuggingFace and this stack's own
Docker daemon, `make download-embedding-model` does the whole thing (export
+ copy into the `onnxmodels` volume) in one step -- not run by `make up`,
same explicit-opt-in posture as `bootstrap-keycloak`.

**Windows/Git Bash footgun found and fixed (finish-brief follow-up):** the
target originally used a bare `--target-dir /tmp/onnx-model-export` and
`docker run -v /tmp/onnx-model-export:/src`. On Windows, Python's own
pathlib silently reinterprets a leading `/` as "root of the current drive"
(so the export actually landed in `C:\tmp\onnx-model-export`), while Docker
Desktop resolves a bare POSIX path like `/tmp/onnx-model-export` against its
own WSL VM filesystem, not the Windows host -- two DIFFERENT locations from
one literal path string. The bind mount was therefore always empty and
`cp -r` silently copied nothing into the volume, with **no error at any
step** -- `make download-embedding-model` reported success while leaving
the volume empty. The backend/workers then found no model file at
`$ONNX_MODEL_DIR`, and every `embed_drawing` task failed -- this is the
confirmed root cause of the "GEO-TEST stuck in `extracting`" observation
from Phase 2 (`docs/ui-qa/log.md`) and its later WALK-1 recurrence
(`docs/ui-qa-report.md`): not a missing manual step, a broken one that
looked like it succeeded. Fixed: the target now uses `$(CURDIR)/.onnx-
model-export` (an unambiguous real path both Python and Docker Desktop
resolve identically) plus `MSYS_NO_PATHCONV=1` (same fix `deploy/keycloak/
bootstrap.sh` already uses for the same class of Git-Bash path-mangling).
Verified end-to-end on this Windows/Git Bash environment: cleared the
volume, ran `make download-embedding-model`, confirmed
`BAAI_bge-small-en-v1.5/model.onnx` (133MB) actually present in the volume
afterward, then confirmed a real drawing upload reaches `ready` with
embeddings (see the finish-brief follow-up's own report for the live
confirmation).

For an air-gapped target (no network access on the machine running the
stack), do the export step on a **separate** machine with network access
instead, using `ai-service/embeddings/download_model.py` directly (it needs
`optimum[onnxruntime]` + `huggingface_hub`, which are intentionally not
part of the backend image):

```bash
pip install "optimum[onnxruntime]" huggingface_hub
python ai-service/embeddings/download_model.py --target-dir ./BAAI_bge-small-en-v1.5
```

Then copy that directory's contents into the `onnxmodels` volume (or, for
the air-gapped target, into wherever that volume's underlying storage lives)
so the result is `<volume>/BAAI_bge-small-en-v1.5/{model.onnx,tokenizer.json,...}`.
`download_model.py`'s own default `--target-dir` (when omitted) now matches
this layout — it previously computed just the HuggingFace repo basename
(`bge-small-en-v1.5`, no `BAAI_` prefix), which never matched what the app
looked for; see `ai-service/README.md` for the full air-gapped procedure.
If the model is missing, `OnnxEmbedder.embed()` raises a `FileNotFoundError`
naming the exact expected path rather than crashing the worker opaquely;
`app/workers/tasks/takeoff.py::_embed_drawing_body` catches it, records the
message on the extraction job row, and re-raises so Celery still marks the
task failed. Module B/C Phase 5's own semantic-matching write paths use
`app.integrations.embeddings::embed_best_effort` instead, which catches
this same `FileNotFoundError` and degrades to leaving the embedding column
NULL rather than failing the request -- see
`docs/module-b-c-phase5-plan.md` §2.

## DWG conversion (ODA File Converter) -- a knowing deviation from the SRS

**The deviation.** `MASTER_SRS.MD` (CAD Ingestion Standard, line 18) says the platform parses **DXF and vector PDF only, "bypassing third-party proprietary CAD runtime licensing (like ODA)"**. That was a deliberate product decision and it is **knowingly reversed** here, by the project owner: real tender drawings arrive as DWG, and asking estimators to re-export every one defeats the point of the takeoff pipeline. DWG is now accepted and converted to DXF by the **ODA File Converter** (a proprietary Open Design Alliance binary), then measured by the unchanged DXF pipeline. Nothing else in the SRS's stance changes: DXF and vector PDF remain first-class, nothing leaves the site, and the platform's own code stays free of any proprietary CAD runtime -- the converter is an isolated, replaceable container, and `DWG_CONVERSION_ENABLED=false` returns the system to the SRS's original behaviour (DWGs are parked with a manual-conversion message).

**Licence position (read before deploying anywhere new).** The package (`ODAFileConverter_QT6_lnxX64_11dll_27.9.deb`, converter v27.9.0.0) ships **no licence file**. Its control file calls it "a free application ... Free to download" (homepage `opendesign.com/guestfiles`), and its About box states: *"This software may not be licensed, sold, distributed or included with other software products without the written consent of Open Design Alliance."* ODA's public download page carries no further terms. Nothing found addresses server-side, automated or commercial use either way. The owner decided to proceed on an **internal-use-only** basis, which means:

- The image is **built locally** from a .deb we hold, and **run only on servers we control**.
- It is **never pushed to a registry, never bundled into a release or another product image, never handed to a customer or third party.** (Moving it between our own machines, e.g. `docker save | docker load` to an air-gapped host, is internal.)
- The .deb and the images built from it are **not committed** (`deploy/vendor/` is gitignored). The `dwg-converter` Compose service is behind the `dwg` profile so nothing tries to build it where the .deb is absent.
- If any of that changes (a hosted/SaaS offering, shipping to clients, a registry), get ODA's **written consent first**; the About-box sentence above is the constraint.

**What was built.**

| Piece | Where | Notes |
|---|---|---|
| `dwg-converter` container | `deploy/dwg-converter/` (Dockerfile, `converter_loop.py`) | Ubuntu 24.04 + `xvfb-run` + the .deb via `dpkg -i` from a local file (`additional_contexts: oda: ./vendor/oda`); **no download of the converter at build or run time**. |
| Sandbox | `docker-compose.yml` | `network_mode: none`, `read_only: true`, tmpfs `/tmp` (1 GB), uid 1000, `cap_drop: [ALL]`, `no-new-privileges`, `mem_limit`/`memswap_limit` 2 GB, `cpus: 1.5`, `pids_limit: 256`. DWG is untrusted input; the converter can reach nothing. |
| Channel | named volume `dwgspool` at `/spool` | No network means no socket, so the converter watches a spool directory instead (job dir with `input.dwg` + `request.json`; it answers with `output.dxf` + `result.json`, and refreshes `heartbeat.json` every 5 s). |
| `celery-worker-convert` | `docker-compose.yml` | Queue **`convert`**, concurrency 1 (the converter is serial and CPU-bound), 512 MB. Has network (Redis/Postgres/S3) but never opens a DWG: it moves bytes between S3 and `/spool`. Always started, even without the converter, so a DWG upload reports "converter not installed" instead of waiting in `queued`. |
| Per-file timeout | `DWG_CONVERT_TIMEOUT_S` (default 120) | Enforced **inside** the converter container by killing the whole process group (ODAFileConverter + xvfb-run + Xvfb); the worker waits that plus a 15 s grace. Verified against the real converter, which stays healthy afterwards. |
| Feature flag | `DWG_CONVERSION_ENABLED` | Empty/unset = **auto** (on while the converter's heartbeat is fresh); `true` = on (a missing converter still parks the drawing with a reason); `false` = off (drawings are parked immediately, nothing is queued). |
| Fixed target | `DWG_TARGET_VERSION` (default `ACAD2018`) | The converter version and target are stored on every drawing. |

New settings are wired through `x-backend-env` and the `backend` service's own environment list; `docker-compose.prod.yml` pins `APP_ENV`/`PRODUCTION_MODE` for `celery-worker-convert` and `check-prod-app-env.sh` checks it.

**Installing the converter on a server.**

1. Put the ODA File Converter Linux **QT6 x64 .deb** at `deploy/vendor/oda/ODAFileConverter*.deb` on that server (copy it from wherever we already hold it; do not download it during a deploy, and never commit it). The file `deploy/vendor/` is gitignored.
2. `make up` (dev) detects the .deb and enables the `dwg` Compose profile itself. For production, which does not go through the Makefile: `docker compose --profile dwg -f deploy/docker-compose.yml -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build`.
3. The image build itself needs the Ubuntu package repositories once (for `xvfb` and the Qt runtime libraries). On a host with **no** internet, build the image on a machine we control that has it, then `docker save installtec-dwg-converter:dev | docker load` onto the server (internal transfer, see the licence bullets), or point apt at an internal mirror. After the image exists, nothing needs the network at run time.
4. Run `make migrate` (migration `0031` adds the derived-file columns to `drawings`; no RLS change).
5. Verify: `docker logs installtec_dwg_converter` prints `converter loop up; ODA version=27.9.0.0`; `docker exec installtec_celery_worker_convert cat /spool/heartbeat.json` shows `"ok": true`; `docker inspect installtec_dwg_converter --format '{{.HostConfig.NetworkMode}} {{.HostConfig.ReadonlyRootfs}}'` prints `none true`. `make dwg-fixtures` runs the real round trip end to end.
6. Upgrading the converter: replace the .deb, rebuild (`docker compose --profile dwg build dwg-converter`) and recreate the container. Existing derived DXFs are kept as they are (each records the converter version that made it); a drawing is only re-converted if its derived file is missing.

**Operating notes.** A drawing shows *needs conversion* (never stuck, never a 500) when: the converter is missing/stopped (`unavailable`/`not_installed`), the file is corrupt, truncated or an unsupported version (`convert_failed`), it exceeds the timeout (`timeout`), or the flag is off (`disabled`). The reason and the manual workaround (re-export as DXF/PDF from AutoCAD/BricsCAD/LibreCAD and upload it) are on the drawing; **Retry conversion** re-queues it. The hourly stale-drawing sweeper parks anything left in `converting`/`queued` past `DRAWING_STUCK_TIMEOUT_S` (a killed worker, or no `convert` worker running) as *needs conversion* too. The derived DXFs are a pure function of the original DWG, so they need no separate backup. Dev note: the converter container ships with `restart: unless-stopped`; stop it (`docker stop installtec_dwg_converter`) to see the "unavailable" path -- the heartbeat goes stale after `DWG_HEARTBEAT_MAX_AGE_S` (30 s).

## Role separation (RLS correctness)

`deploy/postgres/initdb/10-roles.sh` creates two Postgres roles:
- `installtec_migrator` — owns the schema; Alembic connects as this role to run DDL.
- `installtec_app` — `NOSUPERUSER NOBYPASSRLS`, **not** the table owner; the running app and all Celery workers connect as this role for every request/task.

This split exists because Postgres table **owners bypass RLS by default** —
if the app connected as the same role that created the tables, every RLS
policy in the system would silently do nothing. Passwords are read from
`APP_DB_PASSWORD`/`MIGRATOR_DB_PASSWORD` in `.env` (dev-mode plaintext via
Compose env; rotate via `ALTER ROLE ... PASSWORD` in production and inject
through a real secrets manager instead of `.env`).

## Keycloak MFA enforcement — current coverage and gap

`realm-installtec.json` enforces TOTP two ways:
1. `requiredActions.CONFIGURE_TOTP` with `defaultAction: true` — every new user must enrol an authenticator app on first login.
2. `otpPolicyType: totp` at the realm level, so once enrolled, OTP is available for step-up (`acr_values=silver`) flows used by `POST /auth/step-up` before approval decisions.

**Known gap:** a user who removes their own OTP credential (Account Console →
Signing In) is not automatically forced to re-enrol on their *next* login by
`requiredActions` alone — that action only fires for users who never
completed it. Closing this fully needs a custom authentication flow
(`browser-mfa`, cloning `browser` with the `OTP Form` execution set to
`REQUIRED` instead of `CONDITIONAL`) bound as the realm's `browserFlow`. This
was deliberately left out of the JSON export in this slice because a
hand-authored authentication-flow export is easy to get subtly wrong and can
break realm import entirely; add it via the Keycloak admin console (Realm
Settings → Authentication) and re-export, or as a follow-up realm patch.

## Production hardening checklist (not done in this slice)

- Switch Keycloak from `start-dev` to `start --optimized`, set a real `KC_HOSTNAME`, and put it behind TLS (via `docker-compose.prod.yml`'s Caddy service).
- Stop publishing `postgres`/`redis`/`seaweedfs`/`keycloak` ports to the host (`docker-compose.prod.yml` already does this with `!reset []`).
- Replace the demo tenant's `tenant_id` attribute value and remove seed users created by `bootstrap.sh`.
- Rotate `s3-identities.json`'s secret key and the `.env` placeholders.
- Add the `browser-mfa` flow described above.
- Move `celery-beat`'s `--schedule` file off `/tmp` (currently `/tmp/celerybeat-schedule`, see the `celery-beat` service comment) onto a dedicated named volume. `/tmp` is fine for a single dev container but isn't guaranteed to persist across a container restart/recreate on every runtime, and losing it just replays already-due periodic tasks rather than corrupting anything — low risk, but worth a real volume before this is a production deployment.
- **Module C2's PDF/photo extraction path is only verified against `mock-vllm`** (`ai-service/mock-vllm`, a fixed-response FastAPI stand-in — see the `vllm` row above). Every `dev-simulate-quotes` run and every automated test that exercises `extract_quotation` (`app/procurement/quotation_extraction.py`) has run against that mock, never a real vision-language model — mock-vllm's fixed/empty responses are exactly why scenarios (b)/(e) in `docs/c2-verification-report.md` come back `status=extraction_empty` with zero line items; that says nothing about real extraction accuracy. Before relying on this path in production: run `make dev-simulate-quotes` plus 5–10 realistic sample vendor quotes (synthetic — scanned-look PDFs/photos with prices, no real client or vendor data) against `vllm-gpu` (the real image, gated behind the `gpu` Compose profile — see the `vllm` row above) instead of `mock-vllm`, and record extraction accuracy (line items found vs. present, price/unit/currency correctness, false `extraction_empty`/`needs_review` rate) before trusting `is_current` auto-promotion on real vendor replies.

## Intake at scale (migration 0038, branch `fix/intake-scale`)

A real 1,600-file tender took the Docker VM (and Windows with it) down: no container had a memory limit, so the busiest worker
starved the whole WSL2 VM. Full analysis and proof runs: `docs/intake-scale/report.md`.

- **Migrate and rebuild:** `make migrate` (0038 adds `tender_packages.expected_count/paused_at/cancelled_at`, `project_documents.uploaded_at/queued_at/attempts` and three
  indexes), and `make up` so the frontend image (the new upload/tree, `nginx.conf` with `client_max_body_size 300m` and an unbuffered `/api/` proxy) is rebuilt.
  Docker Desktop's WSL2 VM is what is shared with Windows: on a 16 GB laptop give it 10 GB (`%UserProfile%\.wslconfig`: `[wsl2]` `memory=10GB`, then `wsl --shutdown`);
  the limits below are caps inside it, so one runaway container is killed and restarted **alone**.
- **Container limits (dev values, all overridable in `deploy/.env`):**

  | service | `mem_limit` / `cpus` | concurrency (`-c`) | env |
  |---|---|---|---|
  | backend | 1g / 2 | uvicorn | `BACKEND_MEM_LIMIT`, `BACKEND_CPUS` |
  | celery-worker (`ingest,embed`: intake + drawing index) | 2g / 2 | 2 | `INGEST_MEM_LIMIT`, `INGEST_CPUS`, `INGEST_CONCURRENCY` |
  | celery-worker-vlm | 1g / 1 | 1 | `VLM_MEM_LIMIT`, `VLM_CPUS`, `VLM_CONCURRENCY` |
  | celery-worker-email | 384m / 0.5 | 1 | `EMAIL_*` |
  | celery-worker-quotation | 512m / 1 | 1 | `QUOTATION_*` |
  | celery-worker-convert (DWG hand-off) | 512m / 1 | 1 | `CONVERT_*` |
  | celery-beat | 256m / 0.5 | - | `BEAT_*` |
  | dwg-converter (profile `dwg`) | 2g / 1.5 | 1 | (unchanged) |

  Every worker also runs `--max-tasks-per-child=${CELERY_MAX_TASKS_PER_CHILD:-50}` and `--max-memory-per-child=${CELERY_MAX_MEMORY_PER_CHILD_KB:-700000}`, so a child is
  replaced after 50 tasks or as soon as it finishes a task holding more than ~700 MB. `worker_prefetch_multiplier=1` and `task_acks_late` were already set.
  In production set `*_MEM_LIMIT` from the host's real budget (deploy/docker-compose.prod.yml does not override these).
- **New settings (all have defaults, all passed through `docker-compose.yml`):** `INTAKE_MAX_FILES_PER_PACK` (3000: a bigger drop is refused with a message),
  `INTAKE_MAX_FILE_SIZE_BYTES` (250 MiB: the upload limit), `INTAKE_MAX_PROCESS_BYTES` (40 MiB: a bigger file is stored but left under "Needs your check: too large"),
  `INTAKE_DISPATCH_LIMIT` (40 files queued or being read at once), `INTAKE_AI_CONCURRENCY`, `INTAKE_TASK_SOFT_LIMIT_S`/`INTAKE_TASK_HARD_LIMIT_S` (240/300 s per file),
  `INTAKE_UPLOAD_IDLE_S` (60 s: a stalled upload is dropped), `PDF_RENDER_MAX_PX` (5000), `DRAWING_INDEX_SOFT_LIMIT_S`/`..._HARD_LIMIT_S` (300/360 s for a drawing's page index),
  `CELERY_MAX_TASKS_PER_CHILD`, `CELERY_MAX_MEMORY_PER_CHILD_KB`. `INTAKE_MAX_REQUEST_BYTES` (100 MiB) and `INTAKE_MAX_FILES_PER_REQUEST` (50) only bound the old
  multipart endpoints, which still buffer and are kept for scripts and small packs.
- **celery-beat now also runs `intake_tick` every 30 s** (dispatcher + sweeper for intake files). If beat is down, uploads still dispatch immediately and a finished file pulls in the next one;
  only recovery of files abandoned by a dead worker waits for beat. The Redis visibility timeout is 30 minutes (was 1 hour), so a message a dead worker had taken comes back sooner.
- **Reverse proxy:** nginx (`frontend/nginx.conf`) now allows 300 MB bodies and does not buffer request bodies; behind another proxy do the same for
  `PUT /api/v1/tender-packages/*/documents/*/content` (Caddy streams by default).
- **PDF reading:** a page with more than 20,000 drawing objects (a CAD export) is read with PDFium instead of pdfplumber (a real 8 MB A0 sheet took pdfplumber 163 s and 3 GB);
  vector-geometry analysis is skipped above 150,000 objects per page.

### Intake at scale, addendum: memory budget for a 16 GB PC, Postgres, SeaweedFS, drawing queues, AI cost (migration 0039)

- **`%UserProfile%\.wslconfig`** (Docker Desktop's WSL2 VM is what is shared with Windows; the default is half the RAM and no swap):

  ```ini
  [wsl2]
  memory=10GB
  processors=6
  swap=4GB
  ```

  Apply it: close Docker Desktop, run `wsl --shutdown` in PowerShell, start Docker Desktop again, check with `docker info --format "{{.MemTotal}}"` (about 10.5e9).
- **Fit check (measured, the 2,001-file / 3.4 GB proof run):** the largest *simultaneous* total of every `installtec_*` container was **5.8 GiB** (p95 5.5 GiB), with the single peaks
  ingest worker 1.4 GiB (cap 1.5), index worker 1.7 GiB (cap 2), backend 0.47 GiB (cap 1), vlm 0.36, SeaweedFS 1.9 GiB, Postgres 2.4 GiB (page cache included; untuned), Keycloak 0.5.
  The caps added up (always-on set: backend 1 + ingest 1.5 + index 2 + vlm 1 + email 0.375 + quotation 0.5 + convert 0.5 + beat 0.25 = 7.1 GiB, plus SeaweedFS 2.5, Postgres about 1.5 tuned,
  Keycloak and the small ones about 1) are **not** all reachable at once (they peak at different moments), so 10 GB plus 4 GB swap holds with margin for Windows itself; if the VM is
  smaller (the default 7.7 GB), lower `INDEX_MEM_LIMIT`/`INGEST_MEM_LIMIT` and expect OOM-kills of the index worker on big CAD sets (`docker inspect -f '{{.State.OOMKilled}}' <container>`).
  `--profile dwg` (the DWG converter, 2 GiB) is on top of that.
- **SeaweedFS** has `mem_limit: ${SEAWEEDFS_MEM_LIMIT:-2560m}` (measured peak 1.9 GiB plus headroom).
- **Postgres has no `mem_limit`, on purpose**: the kernel OOM-killing the database mid-write is worse than the database using a lot of memory. Its memory is bounded by settings
  instead (`command: postgres -c ...`, all overridable as `PG_*` in `deploy/.env`): `shared_buffers=768MB` (the fixed cost; about 7% of a 10 GB VM), `effective_cache_size=3GB` (planner hint, not an allocation: the page cache it can count on),
  `work_mem=16MB` (per sort/hash per connection, so it is kept modest: the worst case is connections x plan nodes x work_mem), `maintenance_work_mem=256MB` (index builds, vacuum),
  `max_connections=100` (backend pool + 2 ingest + 1 index + vlm + beat children + Keycloak fit with room), `shm_size: 256mb` (parallel queries). The earlier 2.4 GiB peak was mostly page cache and
  unbounded per-connection sorts at the default `work_mem` of the new tuned values' predecessor. These apply to production too (it uses the same base compose file): size them to the host there.
- **Drawing pipeline queues:** `celery-worker-index` (queue `index`, concurrency `INDEX_CONCURRENCY`=1, 2 GiB) runs a drawing's page index and geometry; `celery-worker` (`ingest,embed`) keeps intake and the light tasks. Priority steps 0/3/6/9
  on the Redis broker: 0 a person opened the drawing, 3 the verification report needs it, 6 a bulk "Measure all", 9 automatic on intake. The hard limit of the index task is
  `DRAWING_INDEX_HARD_LIMIT_S` (360 s); a drawing that exceeds the soft limit is marked failed with the reason.
- **Measuring on demand:** intake only classifies and indexes drawings (status `indexed`: number, title, revision, discipline, type from the AI/rules and a sheet count from a light task). Full extraction starts when someone opens the drawing,
  when the verification report is requested, by "Measure all" (lead_estimator and above, audited), or automatically for the disciplines on the managing_director's list (Admin > AI: default none).
  Migration 0039 adds `drawings.measure_priority`, `tenant_ai_settings.intake_auto_measure`, `tender_packages.cost_confirmed_*`, `ai_calls.tokens_cached`. Drawings already routed and never measured stay in whatever status they reached (`queued`/`extracting` ones
  still run when a worker is up; use "Measure all" for the rest).
- **AI cost:** `backend/app/ai/pricing.py` has the Qwen rates (USD per million tokens). `qwen3.7-flash`: input 0.03, cached input 0.006, output 0.13, **measured from the 2026-10 Alibaba invoice**.
  `qwen3.7-plus`: input 0.40, cached 0.08, output 1.20, **UNVERIFIED** (Alibaba's published international price, not yet compared with a bill): the admin AI usage view, the cost estimate and the report all say "unverified" until the first real plus call has been checked.
  Cached prompt tokens (`usage.prompt_tokens_details.cached_tokens`) are billed at the cached rate; unknown models keep the cautious default (5 / 25). Routing: text classification -> `AI_MODEL_CLASSIFY`, page images and drawing/BOQ vision tasks -> `AI_MODEL_VISION`,
  matching and pricing reasoning -> `AI_MODEL_REASONING`; `make ai-smoke` now prints the model each task used, flags a mismatch and marks unverified prices.
  A pack that an external provider would read **does not start (nor resume) until a lead_estimator confirmed its estimated cost** (`GET /tender-packages/{id}/cost-estimate`, `POST .../confirm-cost`, audited); the per-project and monthly budgets stay hard stops.

## BOQ-led estimation agent (feat/boq-agent, 10 Oct 2026): scope change and what it needs

Owner decisions (brief `docs/boq-agent-brief.md`, plan `docs/boq-agent/plan.md`):
- **Upload is a fast, AI-free index.** The per-file AI classification at upload is switched **off by default**: tenant setting `tenant_ai_settings.intake_ai_classify` (migration 0040, default false; the code and the AI path stay and are used when a tenant turns it on).
  With it off, each file gets a **manifest entry** (`project_file_index`: path, size, sha256, PDF page count/sizes, page-1 text, title-block text, sheet names/headers/row counts, rules hints, `partial_index` flag), is classified by the rules only, and only BOQ workbooks and addenda are routed by rules (confidence at or above the auto-accept threshold, no conflict flag). Drawings and everything else wait in the tree; nothing is measured at upload.
- **The agent may fill a draft settlement.** This relaxes "the AI never sets money" **for drafts only**: agent lines carry `cost_source` `agent_candidate` / `agent_estimate`, a person must confirm each one (lead_estimator+, audited) before the settlement can be submitted, and approval (SoD, AED 2m / 8% routing, step-up) is unchanged. The agent never sets quantities, percentages, FX rates, or submits. (Lands with Phase 2.)
- **Search over the manifest** uses a Postgres full-text index and pgvector (HNSW, 384-d, the local ONNX embedder; no external call). Migration 0040 needs the `vector` extension, which the stack already has.
- **Backfill** for packs uploaded before this: `python -m app.cli backfill-manifest --project <code|id>` (or `--all`; `--dry-run` counts). It writes only `project_file_index`; it never changes a document's classification, status or routing.
