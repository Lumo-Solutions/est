- Pre-existing bugs found and fixed while building this phase:
  1. `set_manual_scale`'s ratio computation was semantically inconsistent with `sheet_scale_factor()`'s convention (real metres per *printed/modelled physical* unit): it used the raw two-point pixel/point distance directly. For a DXF sheet this was a no-op (units already physical), but for a PDF sheet (raw distance in points) it would have applied the points-to-metres conversion twice, silently making any calibrated PDF measurement wrong by ~2,835x. Fixed by converting the raw distance through `meters_per_unit(sheet.units)` before dividing. Caught by reasoning through the test math before writing the test, not by a failing test.
  2. `sheet_scale_factor()` did `base * scale_ratio` where `scale_ratio` (a `Numeric(12,6)` column) arrives as a `Decimal` on anything freshly read from the DB -- `float * Decimal` raises `TypeError`. Didn't show up in `set_manual_scale`'s own happy path (its `ratio` is a freshly-computed Python float, never round-tripped through the DB first), only in `revert_scale_calibration` (which restores a `SheetScaleCalibration.ratio` read straight off a DB row). Caught by the integration test suite (`make test-integration`), not unit tests -- unit tests never touch a real Numeric column. Fixed by coercing to `float()` before multiplying.
  3. `drawing_measurements`' DELETE RLS policy (migration 0010) was scoped to `["lead_estimator", "procurement_head", "managing_director"]` on the explicit, previously-true assumption that `recompute_sheet_measurements` only ever ran as a system actor (the Celery extraction task). Phase 4a broke that assumption: `set_manual_scale`/`revert_scale_calibration` call the same function from real request-path actors (any of the five `_UPLOAD_ROLES`, e.g. `estimator`). Under `FORCE ROW LEVEL SECURITY`, a DELETE with no matching policy silently matches zero rows -- so every recalibration by anyone other than `lead_estimator`/`procurement_head`/`managing_director` just ADDED another measurement row instead of replacing the stale one, and `list_measurements()` would non-deterministically return whichever same-kind row its `ORDER BY sheet_id, capability, kind` happened to place first. Not caught by the integration test suite as originally written -- the test that exercised `set_manual_scale` had no pre-existing measurement row to fail to delete, so the bug was invisible there. Only surfaced by running `make dev-simulate-takeoff-pdf` against the real stack (three `alignment_length_m` rows survived one calibrate + one revert, where there should only ever be one) and inspecting `drawing_measurements`/`sheet_scale_calibrations` directly via `psql`. Fixed by migration 0022 (widens `DELETE_ROLES` to match `WRITE_ROLES`) and the integration test was strengthened to seed a pre-existing system-actor measurement first and assert exactly one row survives two estimator-driven recomputes, so this class of bug can't regress silently again.

### §4c: clustered typology recognition

- Branch: `feat/4c-typology-clustering` (from `master`).
- Migration: `0024_typology_clusters.py` -- `typology_clusters`, `typology_cluster_instances`, `typology_variant_deltas` (config-CRUD write policy, `lead_estimator+`, matching `boq_tolerances`/`drawing_layer_trade_mappings`).
- New code:
  - `app/takeoff/typology.py` (pure) -- two independent detection strategies. **DXF**: instances of the same block reference are trivially the same unit regardless of placement/rotation, so grouping is by `GeometricEntity.block_name` directly; a geometric signature (bbox aspect ratio, entity count, total edge length) is a cross-*drawing* consistency check (block names are only unique within one DXF file, so the same name in two different uploaded drawings could mean genuinely different geometry), not the primary key. **PDF**: no block concept exists, so entities are clustered into spatially separate "regions" by bbox proximity (`cluster_by_proximity`, per sheet -- sheets have independent coordinate spaces), each region's vertices centroid-translated and rounded to a self-scaling tolerance grid, then hashed (`normalized_geometry_hash`); matching hashes across sheets become one cluster. Deliberately translation-only, not rotation-invariant, matching the plan doc's literal scope.
  - `app/takeoff/dxf.py::_block_signature_attributes()` -- computes the signature once per distinct `block_name` from the block *definition*'s own local geometry (`doc.blocks[block_name]`), not from any one INSERT's placed/transformed content -- see bug #1 below for why that distinction mattered.

- Design decisions the plan doc left for this phase to make (defaults, not literal spec):
  - `typology_cluster_instances` is one row per **group** (e.g. "type A"), not one row per raw detected repeat -- `instance_count` is the group's total repeat count, `source_handles` (JSONB) is the full traceability list of every repeat's own handle, and `sheet_id`/`bbox_*` give ONE representative repeat's location for the split pane.   - Rollup scoping ("which BOQ items belong to the master") is resolved **spatially on read**, not via a new join table: any `BoqLineItem` linked (`BoqLineItemMeasurement`) to a `DrawingMeasurement` whose bbox (Phase 4b) is fully contained within the master instance's own bbox is in scope. - Known gaps (explicitly out of scope per the plan doc, or narrowed further here):
  1. PDF geometry-hash matching is translation-only, never rotation-invariant -- two copies of the same unit drawn at different rotation angles on a PDF sheet will hash differently and will NOT be detected as the same cluster. Real rotation-invariant hashing (PCA alignment or a rotation search) is a materially harder problem, explicitly out of scope for this first bounded implementation.
  2. The DXF geometric-signature outlier check no longer catches a *non-uniformly-scaled* instance of the same block_name (see bug #1 below) -- an accepted simplification once the signature moved to the block definition's own local geometry; every instance sharing a block_name is now trivially treated as matching, which is correct for the overwhelmingly common case and far more robust against rotation than the per-instance alternative would have been.
  3. Raster (scanned) scale-bar/typology detection is out of scope, same as Phase 4a's own scale-bar detection -- vector geometry only.
  4. Role gating for `/typology-clusters/...` reuses the same pattern as `drawing-layer-trade-mappings` (§4b): no service-layer `_require_role` check, RLS alone enforces `lead_estimator+`, confirmed via a raw `ProgrammingError` in the integration suite, not a dedicated API-level permission test.
- Pre-existing bugs found and fixed while building this phase (both found and fixed before this phase's own code ever reached a passing state -- neither is "pre-existing" in the sense of predating this phase, but both are documented per the brief's own "bugs found" category since neither was caught by writing the test first):
  1. **Scale-invariance self-cancellation in `normalized_geometry_hash`.** Rounding vertices to a grid sized as a percentage of the *same region's own* bounding-box diagonal is, by construction, scale-invariant: for any two similar shapes, `corner / grid` reduces to the identical constant regardless of absolute size (verified: a 10x10 and a 6x6 square hashed identically). Caught by a unit test that expected them to differ. Fixed by adding a log-scale "size bucket" (`round(log(diagonal) / log1p(tolerance_pct/100))`) to the hash payload, which reintroduces absolute-scale sensitivity without losing the intended small-noise tolerance (logging, not dividing by a self-derived value, is what avoids the cancellation).
  2. **Rotation broke DXF block-instance matching.** The original design computed each INSERT's signature from its own world-transformed content (`ezdxf.Insert.virtual_entities()`), which is correct for `entity_count`/`total_edge_length` (rotation-invariant) but NOT for `bbox_aspect_ratio` (a 10x5 rectangle rotated 90° has a 5x10 axis-aligned bbox) -- exactly the "differing only by placement (position/rotation) still match" case the plan doc requires. Caught while writing the DXF fixture test (reasoned through before it ever ran, not from a failing assertion): a rotated placement of the identical block would have been wrongly split into its own outlier group. Fixed by computing the signature once per `block_name` from the block *definition*'s own local (untransformed) geometry instead of any instance's placed content -- rotation-invariant by construction, at the cost of no longer catching non-uniform-scale outliers (known gap #2 above).
  3. **`simulate_typology_pdf` broke on a second run against the same dev database.** `detect_clusters()` is (correctly) project-wide, and this simulation re-uploads the identical fixture geometry every invocation against the shared, never-reset demo project -- so a second run's 40x40 "distractor" rectangle legitimately repeats too (one per prior run) and `detect_clusters()` correctly proposes it as its own separate, valid cluster. The script originally assumed "whichever cluster `detect_clusters` just created is the one we want" and picked up this unrelated distractor cluster instead, failing an `instance_count == 3` assertion meant for the real unit shape. Not a bug in `detect_clusters`/`normalized_geometry_hash` at all -- verified by replicating the exact query+grouping logic standalone (`num_regions=6` for the real shape across two runs' worth of drawings, `num_regions=2` for the now-twice-repeated distractor, both legitimately ≥2). Fixed in the CLI script only: disambiguate by `instance_count == 3` (this fixture's own known shape) across every `pdf_geometry_hash` cluster the project has, not by recency.

1. **`__Host-ins_sid`/`__Host-ins_csrf` cookies were silently dropped by every browser, always**, independent of the Keycloak issue above -- `app/security/cookies.py` hardcodes the `__Host-` prefix, which browsers only accept together with `Secure`, but `deploy/.env.example`'s `COOKIE_SECURE=false` (the old default, from when dev had no TLS anywhere) meant the backend was setting a `__Host-` cookie without `Secure`. Fixed by `COOKIE_SECURE=true` now that `caddy-dev` provides real TLS.
2. **`redirect_uri` came back `http://` even behind an HTTPS proxy**: uvicorn was never given `--proxy-headers`, so `request.url.scheme` never reflected `X-Forwarded-Proto` -- affects **prod too** (`deploy/caddy/Caddyfile` fronts the same way), just never exercised until dev got a TLS hop of its own. Fixed in `backend/Dockerfile`'s `CMD` (and mirrored in the dev override's `command:`, which fully replaces it) with `--proxy-headers --forwarded-allow-ips=*` -- safe because the backend container has no directly-published prod port either (only Caddy is reachable from outside).
3. **`installtec-backend`'s `https://*/api/v1/auth/callback` redirect URI was a no-op**: Keycloak's redirect-URI wildcard only supports a trailing `*` (suffix match), not a wildcard mid-string for the host -- this entry never matched anything, for any host, ever. Fixed by replacing it with the literal `https://localhost:8443/api/v1/auth/callback` in `deploy/keycloak/realm-installtec.json` (and patched the same on the already-imported live realm via `kcadm.sh`, since realm import only re-applies through the exact JSON on first boot).

`deploy/keycloak/dev-token.sh` updated to keep talking to Keycloak's own `:8080` directly (not through `caddy-dev`) -- a password-grant script doesn't need TLS, and the issuer Keycloak stamps into a token is fixed by `KEYCLOAK_HOSTNAME` regardless of which port the request arrived on, so this avoids needing the self-signed cert trusted for a plain CLI tool.

### 3. Margin display precision vs. routing precision

Decision (recorded here, per the ticket's "pick one, record it, test it"): **show margin-on-sell at its full 3dp precision everywhere it drives routing**, rather than rounding the display to 2dp and routing off that. Reasoning: routing already reads the exact 3dp-quantized Decimal (item 2 above); rounding the *display* to 2dp while routing on 3dp would let an approver see "8.00%" for a value that actually escalated to `managing_director` at `7.995%`, which is a materially misleading display of the very thing that drove the routing decision --2dp is fine for money, not for a threshold comparison at the third decimal. Implemented as `frontend/src/lib/format.ts::formatMarginPct` (extracted so it's independently unit-tested -- `frontend/src/lib/format.test.ts`, 3 new vitest tests), used in the cockpit's live simulation panel and the new approval-screen margin display (below).

Two real frontend bugs found while wiring this up and proving it against the real backend (Playwright, not just component tests):
1. **The Approve/Reject controls never rendered for ANY submitted settlement, for anyone, ever**: `SettlementPage.tsx`'s `SubmitApprove` checked `settlement.status === 'pending_approval'`, but `BidSettlementStatus.SUBMITTED` (`backend/app/core/enums.py`) is the string `"submitted"` -- this comparison never matched. Fixed the string; this is what actually makes the settlement Playwright happy path (below) possible at all.
2. **"Build new settlement draft" was unreachable once a project had ever had one settlement**, for the rest of that project's life: the button was gated on `!current` alone, but `build_settlement_draft()` can always be called again (its own docstring: "a rejected settlement is never reopened -- the only way forward is a new version"), regardless of the existing one's status. Fixed with a `REBUILDABLE_STATUSES` set (`approved`/`rejected`/`won`/`lost`) that also shows the button (relabelled "Build new settlement draft") once the current settlement is in a terminal state.
3. **Every `Decimal` field in every `response_model` was silently serialized as a JSON string, not a number** (`"7.995"`, not `7.995`), crashing the first `.toFixed()`/arithmetic call on it in the frontend (blank white page, `TypeError: t[e].toFixed is not a function`) -- found while loading the settlement cockpit for the first time against a real (non-mocked) response. Root cause: FastAPI's `jsonable_encoder()`, when the top-level object is a pydantic `BaseModel` instance (every `response_model` return value), calls that model's own `model_dump(mode="json")` rather than recursing field-by-field with its own (correct, number-producing) `Decimal` handling -- pydantic v2's JSON mode serializes `Decimal` as a string by default. This is **systemic**, not local to settlement -- every other `Decimal`-typed response field in the codebase (costlib, vendors, module_e, etc.) almost certainly has the same latent bug, just never exercised by a real (non-mocked) frontend request before this phase. Fixed narrowly, for what this phase's tests actually exercise: a new `app/schemas/common.py::JsonDecimal` (`Annotated[Decimal, PlainSerializer(float, when_used="json")]`) applied to every `Decimal` output field in `app/schemas/settlement.py` and the two `approvals.py` schemas item 2 touched. **Recommend a follow-up sweep of every other response schema's `Decimal` fields** -- not done here, out of this ticket's proportionate scope.

### Major pre-existing finding: MFA step-up can never reach `acr=silver`

Found while trying to complete `settlement.spec.ts`'s approval through a real login. `deploy/keycloak/realm-installtec.json` defines `"acr.loa.map": "{\"bronze\":1,\"silver\":2}"` on the `installtec-claims` client scope, but the realm import has **no custom `authenticationFlows`** binding any execution (in particular, the OTP check) to Level-of-Authentication 2 -- `acr.loa.map` only *names* the levels, nothing in the imported realm ever *grants* level 2 for completing OTP. Reproduced directly against the real dev Keycloak: a full password + real-TOTP re-authentication via `acr_values=silver&prompt=login` (exactly what `GET /auth/step-up` requests) still comes back `acr=bronze`, so `require_mfa_step_up`'s `ctx.acr < silver` check can never be satisfied by *any* real login, and `approvals.decide()` re-demands step-up forever in a loop no user can escape. This was never caught before because `app/cli.py`'s own settlement simulations construct `RequestContext(acr="silver", ...)` directly (bypassing Keycloak entirely) for exactly this check, and no prior phase drove a real interactive approval.

Not fixed here: this is a security-critical change to the realm's authentication flow, which the build brief itself flags as a "stop and ask" category (weakening or reconfiguring MFA step-up). Raised with the user; agreed plan is a dedicated follow-up on branch `fix/keycloak-step-up` (real Level-of-Authentication-conditional flow bound as the realm's browser flow, `auth_time`-bounded step-up freshness on the backend, dev-only fixed TOTP secrets for automated tests). `settlement.spec.ts` documents this gap inline and asserts the step-up gate correctly fires (and re-fires) rather than claiming a false pass.

## fix/keycloak-step-up: real MFA step-up (branch not yet merged -- awaiting user review)

**Status:** built, test-green -- backend 342 unit (+6 `has_recent_step_up`, +1 stale-acr API test) + 165 integration + 19 API = **526 passed**; frontend 24 vitest (unchanged) + 3/3 real-backend Playwright specs passing, `settlement.spec.ts` now completing a real approval (not stopping at the step-up gate, per Phase 10's note). Not merged to `master` -- left on its own branch for review, since it changes a security-critical authentication flow (per the build brief's own "stop and ask before weakening or reconfiguring MFA step-up" category; the design itself was reviewed and approved by the user before starting, see the chat transcript).

Root cause (Phase 10's finding): `realm-installtec.json` defined `acr.loa.map` (`bronze`:1, `silver`:2) but never bound an authentication flow that actually *grants* either level -- naming levels isn't the same as implementing them. No real login could ever reach `acr=silver`, so `approvals.decide()`'s step-up check re-demanded step-up forever, for every user, always. `app/cli.py`'s own settlement simulations never caught this because they construct `RequestContext(acr="silver", ...)` directly, bypassing Keycloak entirely.

- **`browser-stepup`**: a new realm authentication flow (`deploy/keycloak/realm-installtec.json`'s `authenticationFlows`, bound via `browserFlow`), Keycloak's own documented Level-of-Authentication step-up pattern -- Cookie (ALTERNATIVE) + an "Auth Flow" subflow (ALTERNATIVE) containing two CONDITIONAL subflows in ascending level order: **Level 1** (`Condition - Level of Authentication` level=1/max-age=28800 + Username Password Form + OTP Form -- bronze: password + TOTP at every login, per the SRS's "MFA required at first login") and **Level 2** (level=2/max-age=300 + OTP Form alone -- silver: just the incremental OTP step, since the Cookie authenticator above already reattached the existing bronze session). `deploy/keycloak/bootstrap.sh::ensure_browser_stepup_flow` applies the same structure idempotently via `kcadm` for a realm that already imported the old JSON, so existing dev stacks don't need a realm re-import. Verified against a fresh, isolated `docker run` Keycloak importing the new JSON directly (not just the live dev instance) -- one real bug found there: an over-long `description` field on the flow (496 chars) exceeded Keycloak's `VARCHAR(255)` column and broke the import outright; fixed by shortening it, a mistake that would only ever have surfaced on someone's first fresh `make up`, never on this already-imported dev stack.
- **Critically, `prompt=login` had to come OUT of `app/security/oidc.py::build_authorize_url`'s step-up request**: confirmed live that with it, Keycloak discards the existing SSO session entirely and restarts from Level 1 (password + OTP again) instead of reattaching via Cookie and running only Level 2 (OTP alone) -- the whole point of a lightweight step-up. `GET /auth/step-up` now sends only `acr_values=silver`, no `prompt`; Level 2's own `loa-max-age=300` already forces a fresh OTP entry every time regardless, which is what `prompt=login` was trying to achieve a different (counterproductive) way.
- **`auth_time` claim**: a new `oidc-usersessionmodel-note-mapper` on the `installtec-claims` client scope (same "not in the built-in scopes a from-scratch realm doesn't get" reason `sub`/`acr` already needed their own mappers) -- `acr` alone can't tell a genuinely recent step-up from a still-valid session/token that just happens to carry `acr=silver` from long ago (a refresh_token grant re-mints an access token with the same `acr`, unchanged `auth_time`, no matter how stale). `Principal`/`RequestContext` (`app/security/jwt.py`, `app/core/context.py`) now carry `auth_time`, threaded through both `AuthContextMiddleware` paths and the login audit context.
- **`app/security/deps.py::has_recent_step_up(ctx, settings)`**: the one function every step-up-guarded action now calls -- `acr` rank check AND `(now - auth_time) <= settings.step_up_max_age_s` (new `STEP_UP_MAX_AGE_S`, default 300, matching the flow's own `loa-max-age`). Replaces THREE previously-independent, duplicated `_ACR_RANK`-and-inline-check copies (`approvals.py::decide()`, `procurement.py::_require_dispatch_authority`, and `security/deps.py::require_mfa_step_up`, which was defined but never actually wired into any route) that could have quietly drifted apart. New `tests/unit/test_step_up.py`: bronze (any auth_time) → False, no acr at all → False, silver+fresh → True, silver+just-inside-the-window → True, silver+stale (`auth_time` older than `step_up_max_age_s`) → False, silver+no `auth_time` claim → False (fails closed, not "unknown = fine"). New `tests/api/test_decide_with_stale_silver_acr_is_rejected`: a `decide()` call with `acr="silver"` but `auth_time` 301s old still 403s with `step-up-required` -- this is the exact request the pre-fix code would have let through.
- **Existing integration tests updated, not weakened**: `_ctx()` test helpers across `test_bid_settlement*.py`/`test_procurement_dispatch.py`/`tests/api/conftest.py`'s `authed_client` now default `auth_time` to "just now" whenever a test passes `acr=...`, matching what a real token always carries alongside a real `acr` -- without this, every existing `acr="silver"` test fixture would have started failing the moment `has_recent_step_up` shipped, since `auth_time` would default to `None`.
- **`dev-token.sh` stays bronze-only, on purpose**: scripted/CI bearer-token access must not need TOTP. Keycloak's *built-in* "direct grant" flow has its own `Direct Grant - Conditional OTP` subflow that activates specifically because a user now has a real OTP credential (a side effect of seeding one for interactive login) -- found live, `dev-token.sh` started failing with `invalid_grant` the moment demo users got dev-fixed TOTP credentials. Fixed by disabling that subflow (`bootstrap.sh`), which keeps direct grant exactly as bronze/simple as before regardless of what credentials a user has.
- **Dev-fixed TOTP secrets, not real enrolment, for every demo user by default** (`bootstrap.sh::seed_totp`, guarded by `if [ "$APP_ENV" = production ]`): each demo user gets a raw ASCII secret string seeded directly as `secretData.value` on a real `otp`-type credential (confirmed live, by inspecting Keycloak's own Postgres `credential` table, that this is exactly what a real QR-code enrolment stores -- the base32 string shown to a human is a *display encoding* of these same raw bytes, not what's actually persisted). `frontend/e2e/real-backend/totp.ts`'s `DEMO_TOTP_SECRETS` mirrors the same raw strings; `generateTotp()` now uses `otplib` (MIT) rather than a hand-rolled HMAC implementation, base32-encoding the raw secret first since otplib's functional API expects that form. `deploy/keycloak/dev-reset-totp-user.sh` (Phase 10) remains available for testing genuine QR-code enrolment as a human, unaffected. `deploy/keycloak/dev-prep-login-users.sh` (Phase 10) is now redundant with `bootstrap.sh`'s own default behaviour and was removed.
- **Closed the account-console gap**: `bootstrap.sh` disables the built-in `account`/`account-console` clients -- this app never links to Keycloak's own account management UI, and a user reaching it directly could otherwise delete their only OTP credential (`/realms/installtec/account/` now 404s outright, rather than relying on unverified self-service delete-protection semantics).
- **`frontend/e2e/real-backend/settlement.spec.ts` now runs the full lifecycle for real**: `md1` logs in with its dev-fixed secret (bronze), Approve 403s with step-up-required, `completeMfaStepUp` completes a real incremental OTP re-authentication (no password re-entry -- confirmed it's genuinely the Level 2/OTP-alone path, not a full Level 1 redo), and the settlement reaches `approved`. `global-setup.ts` now calls `make bootstrap-keycloak` directly (idempotent) instead of the two narrower Phase 10 scripts it used before.
- **One self-inflicted bug caught and fixed before it went anywhere**: while manually hunting for a mapper's id via `kcadm get client-scopes/.../protocol-mappers/models -q name=X`, discovered live that `-q` filtering silently does nothing on this specific nested resource (unlike `users -q username=` or `clients -q clientId=`, which do filter server-side) -- a `tail -n1` on the unfiltered list deleted the realm's `tenant_id` mapper instead of the intended one, breaking every login with a 500 (`TokenValidationError: Token has no tenant_id claim`) until restored by hand. `bootstrap.sh`'s own `ensure_mapper` was never affected -- it already checks existence via a client-side exact-line `grep` on the full unfiltered list, not a server-side query -- but this is exactly why: never trust `-q` filtering on an endpoint it hasn't been proven to work on.
